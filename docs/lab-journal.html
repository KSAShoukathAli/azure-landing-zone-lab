CHAPTER 1.1

The network skeleton

Two VNets sit in the same subscription, same region, a few clicks apart. You'd assume they can talk. They can't. Every VNet starts as an island, and the only bridge you get is one you build from both sides.

What got built

Root: terraform/envs/lab. 3 resource groups, 3 VNets, 4 peerings. 10 resources. No subnets, no VMs.

Why two peerings per pair

A peering isn't a cable between two VNets. It's a setting that lives inside one VNet and points at another. peer-hub-to-spoke1 lives on the hub. peer-spoke1-to-hub lives on spoke 1.

Think handshake. One hand out gives you Initiated, and nothing flows. Both hands give you Connected. Azure designed it this way because in a real company the hub and the spoke have different owners, often in different subscriptions. Neither should be able to wire into the other alone.

Allow gateway in X to forward traffic to Yallow_gateway_transitCan the peer use my VPN/ExpressRoute gateway?false
Enable X to use Y's remote gatewayuse_remote_gatewaysDo I use the peer's gateway?false
The idea to keep Peering settings are about what a VNet will accept. They never move a packet. Routes and a forwarder decide where packets go.

Interview line

"A peering is a one-way setting owned by each VNet. You need both halves for Connected, and it only connects those two VNets, never a third."

CHAPTER 1.2

Where does the packet go?

A VM in spoke 1 sends one packet to the hub and one to spoke 2. Same subscription, same region, both spokes peered to the same hub. One arrives. The other is dropped before it ever leaves spoke 1. The hub never even sees it.

What got built

Root: terraform/envs/probes, a separate Terraform root. One subnet, one NIC and one small Ubuntu VM in each VNet, all at .4: 10.60.1.4, 10.61.1.4, 10.62.1.4. 9 resources. No public IPs.

Why a VM at all? Azure keeps the effective route table on the NIC, and a NIC only reports routes when it's attached to a running VM. The VM is just the power supply for the NIC.

Why .4? Azure keeps the first four addresses of every subnet (.0 network, .1 gateway, .2 and .3 DNS) and the last one. .4 is the first you can use.

Separate root, read-only links

The probes root reads the Phase 1.1 VNets through data blocks. A data block is a GET, not a POST. Terraform records what it read in state, but it doesn't manage that resource's lifecycle, so terraform destroy here can't touch the network.

Values you decideValues Azure decides
Names, CIDRs, IPs: keep in localsLocation, resource IDs: read from data

Check after apply: terraform plan in envs/lab said No changes. The subnets created by the second root didn't make the first root want to remove them.

Longest prefix wins

The number after the slash is how much of the address the rule pins down. /8 fixes the first number, /16 the first two. Bigger number, more specific rule. When several rules match, Azure follows the most specific one. Like mail: a letter to Toronto matches "anything to Canada" and "anything to Toronto." You follow the Toronto rule.

The long list of other None rows are the same idea for other private and Azure-reserved ranges. Only four rows matter: own VNet, peer, 10/8 None, 0/0 Internet.

The idea to keep The hub knows routes to both spokes, but knowing a route only helps the hub's own VMs. A packet from spoke 1 never reaches the hub, because spoke 1 drops it first. And spoke 2 has no route back either.
Interview line

"Azure routes by longest prefix match. Peering adds a /16 for the peer only. A third VNet's range falls back to the 10.0.0.0/8 system route with next hop None. To fix it you add something more specific: a direct peering or a UDR to a router in the hub."

CHAPTER 1.3

A route is not a router

You add one route to spoke 1: "send 10.62 traffic to the hub VM." Network Watcher instantly turns green: next hop VirtualAppliance 10.60.1.4. You ping. Nothing. Every tool says yes. The packet still dies. The lesson of this chapter is finding out where.

The envelope

Every packet is an envelope with two addresses. They never change for the whole trip.

From: 10.61.1.4   (spoke 1)
To:   10.62.1.4   (spoke 2)

The hub VM, 10.60.1.4, is never written on it. It's a mailroom along the way.

The five gates

GateSettingWhy it's closed by defaultControlled by
1UDR on spoke 1: 10.62/16 -> VirtualAppliance 10.60.1.4No route, falls into 10/8 NoneTerraform (probes)
2Hub NIC ip_forwarding_enabledAzure won't hand a NIC a packet addressed to someone else (anti-spoofing)Terraform (probes)
3Linux net.ipv4.ip_forward = 1A normal computer drops packets that aren't for itRun Command, not Terraform
4allow_forwarded_traffic on the spoke-side peeringsSpoke 2 sees "From 10.61" arriving from the hub and refuses itTerraform (lab)
5UDR on spoke 2: 10.61/16 -> 10.60.1.4The reply has no route homeTerraform (probes)

Why only the spoke-side peering flags

Forwarded means "the From address isn't in the sender's own range." Follow the envelope. Spoke 1 to hub: From 10.61, arriving from spoke 1. Normal. Hub to spoke 2: From 10.61, arriving from the hub. Forwarded. The hub never receives forwarded traffic, only the spokes do. So only peer-spoke1-to-hub and peer-spoke2-to-hub changed.

Troubleshooting lesson Network Watcher shows gate 1's decision, not delivery. It went green at Stage A and stayed green while the packet died twice more. Check gate by gate. Don't stop at the first tool that looks green.

The proof: TTL 63

spoke1 -> hub      ttl=64   ~1.2 ms   direct over peering
spoke1 -> spoke2   ttl=63   ~2.3 ms   through one router
spoke2 -> spoke1   ttl=63   ~2.4 ms   through one router

Linux starts TTL at 64. Every router subtracts one. Azure's fabric and peerings never touch it. Only the hub VM's kernel did. That missing 1 is proof the traffic went through the hub.

Two route tables, two layers

Inside every VM, Linux has one rule: send everything to the subnet gateway (via 10.61.1.1, via 10.60.1.1). Linux knows nothing about peerings or UDRs. Azure applies the effective route table after the packet leaves the VM. Linux decides whether to forward. Azure decides where it goes next.

New Terraform tricks

  • count = var.x ? 1 : 0 as an on/off switch. Switches live in phase3.auto.tfvars, which Terraform loads automatically.
  • A UDR is three resources: route table, route, and the subnet association. Without the association nothing uses it. Route tables attach to subnets.
  • One resource, one owner. Route tables and the NIC flag went in probes (owns subnets and NICs). Peering flags went in lab (owns peerings). Each root is planned and applied on its own.
  • (known after apply) means Azure will tell Terraform the value at creation: IDs, and read-back lists like a route table's route and subnets.
  • Outputs built from resource attributes stay true. Hardcoded output text goes stale. The old "No UDR" output was replaced with one that lists the real routes.

In real hub-and-spoke designs, spoke-to-spoke and internet egress go through the firewall. Traffic inside one spoke stays local and is filtered with NSGs. One summary UDR like 10.0.0.0/8 -> firewall covers every spoke.

Interview line

"Peering isn't transitive and a VNet doesn't forward packets, so spoke-to-spoke needs a router in the hub. I built it with a Linux VM and opened each layer: UDRs on both spokes, IP forwarding on the NIC, IP forwarding in the OS, and allow-forwarded-traffic on the spoke peerings. Network Watcher went green at the first UDR, but packets only flowed once all layers were open, and TTL dropped from 64 to 63. In production that's Azure Firewall, which forwards natively but denies by default."

CHAPTER 2.0

Scopes, management groups and CAF

A company has 50 subscriptions, one per app team per environment. Security says: no public IPs in app subscriptions, Canada Central only, everything tagged. You can assign 150 policies by hand. Then team 51 gets a subscription and somebody forgets.

The scope hierarchy

Tenant (Entra ID directory)
 +-- Tenant Root Group          created automatically, one per tenant
      +-- Management group      a folder for subscriptions (nests up to 6 levels)
           +-- Subscription     billing and quota boundary
                +-- Resource group   lifecycle folder
                     +-- Resource

Anything assigned at a scope flows down to everything below it, both Azure Policy and RBAC. A child can't override a parent's Deny. The only way out is an exemption granted from above. That's why an app team can be Owner of its subscription and still not break platform rules.

CAF, built one folder at a time

The Cloud Adoption Framework is Microsoft's playbook, not a product. Its landing zone design is a standard management group tree:

Tenant Root Group
 +-- Contoso                    company rules: regions, tags
      +-- Platform              run by the platform team
      |    +-- Connectivity     hub VNet, firewall, VPN    (your hub RG)
      |    +-- Identity
      |    +-- Management       Log Analytics, monitoring
      +-- Landing Zones         run by app teams
      |    +-- Corp             internal, peered to hub, no public IPs   (your spoke RGs)
      |    +-- Online           internet-facing apps
      +-- Sandbox               playground, not connected to the hub
      +-- Decommissioned        being shut down, no new deployments

Rules stack down. A Corp subscription gets Contoso's rules, Landing Zones' rules and Corp's rules. Connectivity sits under Platform, so the "no public IPs" rule never reaches the hub. That's why the hub can hold a firewall with a public IP.

What a landing zone is A subscription that's ready before the app team arrives: already in the right folder, already peered to the hub, already sending logs to Management. The team lands and builds. In this lab, each spoke is a landing zone.

Terraform mirrors the tree

CAF pieceTerraform rootOwner
Management groups and policygovernancePlatform or security
ConnectivityconnectivityPlatform network team
ManagementmanagementPlatform ops
Each landing zonelanding-zones/<team>Platform creates, app team builds inside

Separate state, separate pipeline, separate least-privilege identity. Blast radius stays small. This repo already splits governance, lab and probes. Phase 3A moved the spokes into a shared module inside lab (chapter 3A). Phase 3B will split lab into connectivity and landing-zones/spoke1, spoke2, both calling that module. Producing new landing zones from a standard module is called subscription vending. Microsoft's own Terraform for the full tree is Azure Landing Zones (ALZ), now moving into Azure Verified Modules.

Interview line

"Management groups are folders above subscriptions. Policy and RBAC assigned there are inherited, and a child can't override a parent's Deny. CAF separates Platform (Connectivity, Identity, Management) from Landing Zones (Corp, Online), and I structure Terraform the same way: separate roots and pipelines per piece, with new landing zones vended from a standard spoke module."

CHAPTER 2.1

Policy deny, in isolation done

Your deployment identity is Contributor. RBAC says yes. Terraform plan is green. You apply, and Azure says no. How?

Designed with ChatGPT, run with Claude. Two roots with separate state, playing two different owners. Nothing touches the hub-and-spoke network.

What got built

RootPlaysOwnsResult

policy-lab/workloadApp teamA data block reading the RG, one Standard public IP pip-should-be-denied-cacPlan 1 to add. Apply 403.

The RG took 24 seconds. The definition and the assignment took about 1.5 minutes each. Policy objects are replicated globally, and Azure waits until they're visible everywhere before calling them done.

Definition vs assignment

A definition is the rule. Yours is tiny: if type is public IP, then deny. An assignment puts that rule on one scope and makes it live. Think of a rule in a library and a sign on a door. One rule, many doors.

ObjectCan live at
DefinitionManagement group or subscription. Never a resource group.
AssignmentManagement group, subscription, resource group, even one resource. Must be at or below its definition.

Two settings decide what an assignment actually does. enforcementMode (Terraform calls it enforce) decides whether it runs. The effect in the definition decides what it does. The subscription already carried Microsoft's ASC Default initiative, also enforced. It blocks nothing because its effects only audit.

Plan only reads. Policy only judges writes.

Here's everything terraform plan does: read your .tf files, read state, send GETs to refresh what exists, compare, print. It never sends the PUT that says "create this." Azure Policy lives inside Resource Manager and checks each PUT as it arrives. No PUT, no policy check.

It has nothing to do with whether the resource is in state. Change an existing resource in a way the policy dislikes, and plan is still green. Apply still fails.

ControlQuestion it answersChecked when
RBACIs this identity allowed to do this action?Every request
Azure PolicyIs this resource allowed to exist, in this shape, here?When Resource Manager receives the create or update

Catching it earlier: in a pipeline, export the plan with terraform show -json and check it with Checkov or OPA, so the failure shows up on the pull request. Azure Policy stays the final gate, because the person clicking in the portal never goes through your pipeline.

Interview line

"I assigned a custom Deny policy to a resource group, then had a separate Terraform root try to create a public IP there. Plan was green, because plan only reads and policy only judges writes. Apply got a 403 RequestDisallowedByPolicy naming the exact assignment, and nothing was created. A green plan proves the config is valid, not that it's allowed."

Guardrails on the landing zone done

Friday afternoon. Someone opens the portal and creates a public IP in spoke 1, in East US, with no tags. Monday, security finds an internet-facing endpoint that bypasses the hub, in a region you don't support, owned by nobody.

2.1 asked whether Azure Policy works. 2.2 asks which rules a real landing zone needs, and puts them on your actual hub and spokes. Three problems in that story, one rule each.

Root: terraform/envs/governance. Owns only policy assignments, so destroy removes only the guardrails.

The hub is exempt from the public IP ban, which is the CAF Connectivity versus Corp split in miniature. The tag is managed_by, which every Terraform resource here already carries.

You don't write the rules

In 2.1 you wrote a definition. Here you don't. Microsoft ships these as built-in definitions, and you look them up by fixed GUID. Each one is a blank form. "Allowed locations" says only allow these regions: ____. You fill the blank with a parameter when you assign it.

Terraform: one for_each block per guardrail makes one assignment per RG. The public IP block filters out the hub with if k != "hub". Each assignment carries a non_compliance_message, so a blocked person reads "deploy only to canadacentral" instead of a bare policy ID.

Before applying: what already exists

A read-only check listed every resource in the three RGs against the three rules. 14 resources: 3 VNets, 3 NICs, 3 VMs, 3 OS disks, 2 route tables. All 14 passed.

The disks were the interesting ones. Terraform never created them. It asked for a VM, and Azure made the disk as a side effect. They still carry managed_by, because the VM's tags were carried onto the disk at creation.

Subnets, peerings and routes didn't appear at all. They're child resources and can't hold tags. The tag policy skips anything untaggable, or nobody could ever create a subnet.

The questions, answered
  1. Deny is assigned after the VNets and VMs exist. What happens to them? Nothing. Deny judges requests, not resources. A non-compliant existing resource would only show up on the Compliance page. The next update to it, though, is a PUT, and gets judged.
  2. Why is the hub allowed public IPs but the spokes are not? The hub is the internet edge. Spokes route through it, the same way spoke-to-spoke traffic does in 1.3. Tests C and E show it.
  3. Terraform resources pass the tag rule. What happens to someone using the portal? The portal sends the same PUT. They get test B's denial and test B's message, until they add the tag.
The idea to keep Enforcement happens at each PUT, instantly. Compliance reporting is a separate, slower scan. A Compliance page that says "Not started" doesn't mean the Deny is off. Test with a create.

CHAPTER 4.0

Remote state and plan on PR done

You open your first pull request. GitHub starts a fresh Linux runner, checks out your code and runs terraform plan. It looks at Azure and sees ten resources. It checks its memory and finds nothing. Plan: 10 to add.

The runner isn't wrong. It just never saw the state file sitting on your laptop.

Why local state stops working

State is Terraform's memory. It's how Terraform knows "these ten Azure resources are mine, and this is what they looked like last time." It never goes into git, because it changes on every apply and can hold secrets. So while it lives on your laptop, only your laptop can plan correctly.

The fix is to keep it somewhere both your laptop and the runner can reach. In Azure, that's a blob.

The bootstrap root

The storage has to exist before any root can keep state in it. And it can't keep its own state inside itself. So it gets a tiny root of its own, terraform/bootstrap, whose state stays local forever. You run it once and rarely again. 4 resources.

That's the data plane, and it has its own roles. With shared keys off, a data role is the only way in. Without it, migrate-state fails with a 403 even though you "own everything."

Moving the memory

Each root got a backend.tf: same account, same container, different key. Plus use_azuread_auth = true, or Terraform goes looking for a storage key that no longer exists. Then terraform init -migrate-state. It asks before it copies, and it wants the full word yes. Type y and it just asks again.

Lineage is the state file's identity, stamped once when it's first created. Serial counts writes. Copying into the new backend was one more write, so serial went up by one. Same identity, one version newer.

The local terraform.tfstate was left behind as a 0-byte file. That's deliberate. A full leftover copy could be picked up by mistake later, so Terraform empties it once the remote copy is in charge.

Something new showed up too: Acquiring state lock. The backend takes a lease on the blob while Terraform works, so you and CI can't write at the same moment. Local state never protected you from that.

How the runner logs in without a secret

The old way was a service principal with a client secret pasted into GitHub. That secret lives forever, leaks, and expires at the worst moment. With OIDC, GitHub issues a short-lived token on every run that describes the run. Entra trusts it only if its subject matches a federated credential you set up in advance. Terraform does the swap itself (ARM_USE_OIDC=true), so there's no azure/login step.

repo:KSAShoukathAli@275120224/azure-landing-zone-lab@1443587946:pull_request

The two numbers are the owner ID and the repo ID. Since July 15, 2026, GitHub puts them in the subject for every new or renamed repo. The old subject trusted a name, and names get reused: delete a repo, someone creates one with the same name, and their workflow matches your trust. IDs are never reused. A name-only subject on this repo would fail with an AADSTS "no matching federated identity" error. Helpfully, that error shows the subject GitHub actually sent.

The :pull_request ending means only PR runs get this identity. A push to main can't. That's on purpose. This is the plan identity, and apply gets its own identity and subject later.

Nothing at subscription scope. Governance was the open question: it looks up three built-in policy definitions at /providers/Microsoft.Authorization/..., outside any RG. CI read them fine with RG-level Reader.

Client ID, tenant ID and subscription ID are GitHub variables, not secrets. They're identifiers. Without a matching GitHub token they open nothing.

A user-assigned managed identity takes the same federated credential and fits better. It can't hold a secret at all, so OIDC is the only way in. It lives in an RG and is governed like any resource. And plain azurerm Terraform can create it. Swapping later changes one GitHub variable.

The workflow

.github/workflows/terraform-plan.yml runs on pull_request, never pull_request_target, which runs with the base repo's privileges against code from a fork. It plans lab and governance side by side, with Terraform pinned to 1.15.8, the same as your laptop. Permissions are contents: read and id-token: write. That second one is what lets the job ask GitHub for a token at all.

The side effect: CI goes blind

Nothing in the code was wrong, and the next PR would still have failed. Here's why.

Plan compares three things: the code (from the checkout), the state (from the blob) and the real resources (from Azure). How GitHub proves who it is
  1. GitHub signs a short-lived token with its own private key. Its sub claim describes the run: repo:KSAShoukathAli@275120224/azure-landing-zone-lab@1443587946:pull_request.
  2. Terraform sends that token to Entra with client_id (which app to log in as). The tenant ID is in the URL.
  3. Entra checks GitHub's signature with GitHub's public keys, then compares iss, sub and aud with the app's federated credential. Exact match, or no.
  4. Entra returns an Azure token for the app's service principal. RBAC then checks that service principal's roles on each resource.
AZURE_CLIENT_ID, AZURE_TENANT_ID and AZURE_SUBSCRIPTION_ID are GitHub variables, not secrets. They're lookup keys. Without a GitHub-signed token with the right subject, they open nothing.

Why the app registration has to go

Anyone who can manage an app registration can add a client secret to it. With that secret, they log in from a laptop as the CI identity, and OIDC is never checked. A user-assigned managed identity can't hold a secret or a certificate at all, so federation is the only door. It also lives in an RG like any other resource, gets cleaned up with it, and can be created with plain azurerm, without tenant-wide Graph permissions.

What delegation means

A delegated subnet is handed to one Azure service. The service can drop its own network cards into it whenever it scales. You keep owning the address range, but you can't put anything else there. That's why APIM and the Logic App each get their own subnet even though both use Microsoft.Web/serverFarms. And Flex Functions can't share with either. Its delegation is Microsoft.App/environments, the one Microsoft.App had to be registered for in 7.1A.

These three subnets carry outbound traffic only. The app calls out through them. Anything calling in to the app arrives through a private endpoint in snet-pe.

The trap that would have shown up every night

Each delegation carries a list of actions, and Azure fills it in if you leave it out. The azurerm provider doesn't read it back the same way. So a delegation written without actions would plan "1 to change" on every run, forever. And the nightly drift check would cry wolf every night.

The module states them, and the change script checks them against Azure's own list before writing a single file:

delegation_actions = {
  "Microsoft.Web/serverFarms"  = ["Microsoft.Network/virtualNetworks/subnets/action"]
  "Microsoft.App/environments" = ["Microsoft.Network/virtualNetworks/subnets/join/action"]
}

Both matched. The re-plan after apply came back clean, which is the real proof.

You open a PR in the portal. CI plans it, you read the plan, you merge. Then you go back to PowerShell, pull main, run an apply script, type yes, run a verify script. Half the work is in the browser, half is in scripts, and you can't see what the scripts are doing unless you read them.

"Why are we branching and merging through scripts? That's not how I work." Fair. So the second half moves into GitHub too.

This was planned for 7.3. It got pulled forward because the manual apply was the confusing part. Now, for the lab root, the whole loop happens in the GitHub portal and you can watch every step.

The two halves

open PR  --> terraform-plan:  plan, upload plan, summary         (review proof)
merge    --> terraform-apply: plan on main, upload saved plan
         --> waits for you:   "Review pending deployments"
         --> apply that exact file, then re-plan must be clean

The plan you approve is not the one from the PR. It's a fresh plan made on main after the merge.

Why? Two PRs, A and B. You open both, B merges first. A's plan was made before B existed. Apply it and you could undo B, or fail halfway. A plan made on main after the merge always starts from what's really there. Terraform also refuses a saved plan if the state moved since it was made, so a stale plan can't sneak through.

Two keys, two doors

The apply identity lives in terraform/bootstrap. You apply bootstrap yourself, so the pipeline can never give itself more rights. Contributor can change resources but can't assign roles or change policy, so it can't touch the guardrails either.

Its trust is the important part. Only a job running inside the GitHub environment lab-apply can get its token. A PR branch can't. A plain push to main can't. And lab-apply has you as its required reviewer. No approval, no token, no write.

The approval is the token The Approve button isn't a courtesy pause in a script. GitHub only issues the token that matches the apply identity's trust after the environment's protection rule passes. Until you click, the job has no way to write to Azure at all.

The ruleset, and why 0 approvals

main-protection on the default branch: no deletions, no force pushes, a PR for every change, and plan (lab) and plan (governance) must pass. The PR workflow lost its paths filter for this. A required check that never runs leaves a docs-only PR waiting forever.

Required approvals is 0, not 1. GitHub never lets the author approve their own PR, and you're the only person in the repo. With 1, nothing could ever merge. So in this lab the human check sits at deploy time, in lab-apply. In a team you'd require one review from CODEOWNERS on top.

CHAPTER 7.1B DNS

Seven zones, fourteen links done

Picture 7.2. Key Vault gets a private endpoint at 10.63.1.4 and public access is switched off. The Logic App calls kv-dev.vault.azure.net, DNS hands back the public IP, and Key Vault refuses the connection. The private endpoint is there and working. Nobody told the Logic App its address.

A private endpoint gives you a private IP. DNS is what makes an app find that IP using the normal service name. You need both, and this chapter builds the DNS half before there's anything to resolve.

Four things that sound alike

The server answers. The zone stores. The link decides who's allowed to ask. The private endpoint is the address being looked up.

Following one lookup

Only names that public DNS sends into privatelink.* are affected. A service only gets that CNAME once someone gives it a private endpoint. A plain public storage account never touches our zones.

Why seven, and why the hub

Each service has a fixed private zone name. You don't choose them. Storage alone needs four, because one account has four separate endpoints (blob, queue, table, file), and a Logic App Standard uses all four for its runtime.

ZoneFor
privatelink.vaultcore.azure.netKey Vault

No Service Bus zone. Service Bus stays Standard and public, and private endpoints need Premium.

One copy of each zone, in the hub, owned by platform. A VNet can link only one zone of a given name. Give each spoke its own copy and some VNets see half the records.

Links, and the decisions behind them

A zone sitting in the hub RG doesn't serve the hub VNet. An RG is a management folder, not a DNS boundary. And peering carries packets, not DNS. Every VNet that needs the private answers gets its own link. That's 7 zones times 2 VNets, built with setproduct so a new VNet is one map entry.

What happens when the record isn't there

Say someone gives kv-other a private endpoint, but its record isn't in our zone. From integration-dev, public DNS still sends the lookup into privatelink.vaultcore.azure.net, and our zone has nothing.

Your call was the simple one. Key Vault will have public access off. A fallback would only swap a clear DNS error for a confusing access error later. Redirect is for VNets that must reach other teams' or other companies' private-endpoint services that you'll never have records for.
